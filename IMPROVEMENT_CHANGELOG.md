# TraceGuard X — Improvement Changelog

This changelog records the major evaluator iterations, the hypothesis behind
each change, the evidence used to assess it, and the resulting decision.

The benchmark and evaluation artifacts are generated by the project. No
benchmark percentages are manually inserted into the evaluator.

---

## 0 — Baseline

**Hypothesis:**  
A single evaluator can judge a coding-agent trajectory primarily from the
agent's narrative and reported test results.

**Evidence:**  
The baseline evaluator uses the trajectory's stated verdict and reported
execution information without independent sandbox verification.

**Decision:**  
Keep as the control condition for measuring the value of independent
verification.

**Implementation evidence:**

- `baseline/baseline.py`
- `artifacts/baseline_results.json`

---

## 1 — Trace Normalization

**Hypothesis:**  
Structured trace fields make agent claims easier to inspect and compare.

**Evidence:**  
The advanced pipeline normalizes trajectory information into explicit fields
for the claimed verdict, test claims, output claims, candidate code and
verification context.

**Decision:**  
Keep structured trace normalization as the first advanced-processing stage.

**Implementation evidence:**

- `src/traceguard/pipeline.py`
- `agents/trace_analyst.md`
- `trajectories/trace_analyst.jsonl`

---

## 2 — Static Verification

**Hypothesis:**  
Syntax and static checks can detect obvious implementation failures before
expensive independent execution.

**Evidence:**  
The advanced pipeline performs static validation before allowing candidate
code to proceed through the execution path. Syntax failures can therefore be
identified without relying on the agent's narrative.

**Decision:**  
Keep static verification as an early, deterministic verification stage.

**Implementation evidence:**

- `src/traceguard/pipeline.py`
- `agents/static_analyzer.md`
- `trajectories/static_analyzer.jsonl`

---

## 3 — Independent Docker Sandbox

**Hypothesis:**  
Independent execution can expose false-success narratives that cannot be
trusted from the agent's report alone.

**Evidence:**  
The advanced executor runs candidate code in an isolated Docker environment
with network isolation, read-only filesystem configuration, dropped
capabilities, resource limits and a timeout.

Runtime failures and incorrect observed outputs therefore provide evidence
independent of the agent's reported success.

**Decision:**  
Keep independent sandbox execution.

**Why this matters:**  
This became the most important evaluator improvement because it converts an
agent claim into independently observable execution evidence.

**Implementation evidence:**

- `src/traceguard/tools/sandbox.py`
- `SECURITY.md`
- `Dockerfile`
- `trajectories/execution_agent.jsonl`
- `artifacts/advanced_results.json`

---

## 4 — Claim / Evidence Reconciliation

**Hypothesis:**  
A contradiction between what the agent claims and what verification observes
should be represented explicitly instead of being buried in prose.

**Evidence:**  
The evaluator compares reported success claims with independently observed
execution facts such as exit status, test counts and output.

The resulting findings include explicit
`claim_evidence_contradiction` categories.

**Decision:**  
Keep claim/evidence reconciliation as a dedicated evaluation stage.

**Implementation evidence:**

- `src/traceguard/pipeline.py`
- `agents/auditor.md`
- `trajectories/auditor.jsonl`
- `artifacts/advanced_results.json`
- `artifacts/comparison.json`

---

## 5 — Deterministic Scoring

**Hypothesis:**  
Evaluation scores should be reproducible from observable evidence rather than
being freely generated by a language model.

**Evidence:**  
The scorer calculates the final score from deterministic dimensions including
test pass rate, property verification, evidence coverage, claim consistency,
robustness and static code quality.

**Decision:**  
Keep deterministic scoring.

**Implementation evidence:**

- `src/traceguard/scorer.py`
- `evaluation/compare.py`
- `artifacts/comparison.json`

---

## 6 — Requirement Graph and Verification Planning

**Hypothesis:**  
Running only the tests claimed by an agent is insufficient. Requirements
should become explicit verification targets, including additional
high-value checks.

**Evidence:**  
The advanced workflow converts requirements into inspectable verification
targets and uses bounded verification planning to select additional
checks and edge cases.

**Decision:**  
Keep requirement extraction and bounded verification planning.

**Implementation evidence:**

- `agents/requirement_agent.md`
- `agents/verification_planner.md`
- `agents/adversarial_verifier.md`
- `trajectories/requirement_agent.jsonl`
- `trajectories/verification_planner.jsonl`
- `trajectories/adversarial_verifier.jsonl`

## 7 — Property Verification

**Hypothesis:**  
Fixed examples alone may miss behavioral failures. Independent properties
should provide another layer of verification.

**Evidence:**  
The evaluator calculates property evidence separately from ordinary test
results and incorporates it into functional correctness and scoring.

**Decision:**  
Keep property verification as an independent evidence source.

**Implementation evidence:**

- `src/traceguard/pipeline.py`
- `src/traceguard/scorer.py`
- `artifacts/advanced_results.json`

---

## 8 — Evidence Coverage and Human Review

**Hypothesis:**  
Incomplete verification should not silently become a confident PASS.

**Evidence:**  
The evaluator distinguishes candidate failures from verification
infrastructure problems such as `sandbox_timeout` and `verification_gap`.
Incomplete evidence can trigger `human_review_required`.

**Decision:**  
Keep explicit verification-gap handling and human-review gating.

**Implementation evidence:**

- `src/traceguard/scorer.py`
- `src/traceguard/pipeline.py`
- `artifacts/advanced_results.json`

---

## 9 — Mutation Testing

**Hypothesis:**  
The evaluator itself should be tested against realistic faults rather than
being assumed to work correctly.

**Evidence:**  
The mutation suite injects realistic evaluator faults and records whether the
evaluation system detects them.

The generated mutation artifact records:

- total mutations;
- killed mutations;
- mutation detection rate.

**Decision:**  
Keep mutation testing as an evaluator self-challenge.

**Implementation evidence:**

- mutation-testing implementation
- `artifacts/mutation_report.json`

## Removed Experiment — LLM Judge Debate

**Hypothesis:**  
Running multiple language-model judges that debate every case could improve
evaluation reliability.

**Observed tradeoff:**  
The additional model-judge layer increased latency, cost and architectural
complexity without providing enough measured benefit to justify keeping it.

**Decision:**  
Remove the LLM judge debate from the final evaluator.

**Lesson:**  
More model reasoning is not automatically more reliable. In this system,
independently generated execution and verification evidence provides a more
useful reliability boundary than another layer of model agreement.

**Final design consequence:**  
Language-model-style interpretation can help organize or explain evidence,
but deterministic execution facts remain authoritative for hard verification
decisions.
